# tux Design Notes

tux is a framework for building terminal application interfaces in Go. Its full name is Terminal User Experience.

The core idea is simple: **the interface structure is written in XML, state and behavior are written in Go, and the XML compiler generates ordinary Go code from the interface structure.**

This document is written for people and agents seeing tux for the first time. Read it progressively: start with the workflow, then the XML compilation rules, then the framework internals.

## 1. Workflow

When using tux, a component usually consists of two files:

- A Go file: stores state, constructors, and event handlers.
- An XML file: describes the component's interface structure.

For example, suppose we want to build a page that displays a title and has an input field for editing a name.

The Go file owns state and behavior:

```go
package components

import "github.com/open-portfolios/codefolio/pkg/tux"

type home struct {
    tux.Composite

    title *tux.State[string]
    name  *tux.State[string]
}

type HomeProps struct{}

func Home(props HomeProps) tux.Component {
    return &home{
        title: tux.NewState("Welcome"),
        name:  tux.NewState(""),
    }
}
```

The XML file owns the interface structure:

```xml
<component package="components" name="home">
  <Box str="page">
    <Text str="@{self.title}" />
    <Input state="{self.name}" />
  </Box>
</component>
```

The XML compiler generates `*_tux.go`:

```go
package components

import (
    tux "github.com/open-portfolios/codefolio/pkg/tux"
    builtin "github.com/open-portfolios/codefolio/pkg/tux/builtin"
)

func (self *home) Build(ctx tux.BuildContext) tux.Component {
    return builtin.Container(
        builtin.ContainerProps{},
        builtin.Box(
            builtin.BoxProps{
                Str: "page",
            },
            builtin.Text(
                builtin.TextProps{
                    Str: self.title.Get(ctx),
                },
            ),
            builtin.Input(
                builtin.InputProps{
                    State: self.name,
                },
            ),
        ),
    )
}
```

Users do not hand-write `Build(ctx)`. XML generates it.

Even when a component has no XML props, it still uses an empty props struct such as `HomeProps{}`. This keeps every component constructor explicit about its props parameter.

## 2. Why Split XML And Go

Go is good for state, events, and business logic, but Go does not have named parameters. If interface trees are described directly with Go function calls, argument order becomes hard to maintain.

tux uses an `XxxProps` struct as the argument container:

```go
builtin.Input(builtin.InputProps{
    State: self.name,
})
```

XML attributes are naturally named:

```xml
<Input state="{self.name}" />
```

Therefore, the tux XML compiler only needs to convert XML attributes into `XxxProps` fields. The XML stays readable, and the generated Go code is still checked by the Go compiler.

## 3. File Convention

Each XML file contains exactly one `<component>` root node and generates one `*_tux.go` file.

For example:

```text
home.go
home.tux.xml
home_tux.go
```

`home.go` is handwritten by the user.

`home.tux.xml` is the handwritten interface file.

`home_tux.go` is generated by the compiler.

## 4. Package Paths

The tux root package is fixed:

```go
github.com/open-portfolios/codefolio/pkg/tux
```

Builtin components live in:

```go
github.com/open-portfolios/codefolio/pkg/tux/builtin
```

The XML compiler automatically injects the tux root import and builtin import:

```go
import tux "github.com/open-portfolios/codefolio/pkg/tux"
import builtin "github.com/open-portfolios/codefolio/pkg/tux/builtin"
```

Builtin components do not need explicit `<import>` nodes in XML. They can be used directly:

```xml
<Text str="hello" />
<Input state="{self.name}" />
<Container />
```

Non-builtin component packages explicitly imported from XML are named `p1`, `p2`, `p3`, and so on:

```go
import p1 "myapp/components"
```

This keeps user component package aliases from conflicting with the root alias `tux` and builtin alias `builtin`.

## 5. XML Root Node

The root node must be the lowercase `<component>` node:

```xml
<component package="components" name="home">
  ...
</component>
```

Meaning:

- `package="components"` means the generated file uses `package components`.
- `name="home"` means the compiler generates a `Build(ctx)` method for `*home`.

Generated result:

```go
package components

func (self *home) Build(ctx tux.BuildContext) tux.Component {
    ...
}
```

`<component>` is a tux meta node, not a normal interface component.

## 6. XML Import

XML uses `<import>` to declare non-builtin components. Builtin components come from `github.com/open-portfolios/codefolio/pkg/tux/builtin`; the compiler imports them automatically, so they do not need `<import>`.

```xml
<import package="myapp/components" component="Box" alias="MyBox" />
```

Rules:

- `package` is the Go import path.
- `component` is the Go constructor function name.
- `alias` is the XML tag name.
- If `alias` is omitted, the XML tag name equals `component`.
- The same package path reuses the same `pN` alias.

For example, suppose the user also defines a `Box` component in their own package. To avoid colliding with builtin `<Box>`, XML can name it `<MyBox>` with `alias="MyBox"`:

```go
package components

import "github.com/open-portfolios/codefolio/pkg/tux"

type BoxProps struct {
    Title string
}

func Box(props BoxProps, children ...tux.Component) tux.Component {
    // handwritten component
}
```

Another XML component can import and use it like this:

```xml
<component package="pages" name="dashboard">
  <import package="myapp/components" component="Box" alias="MyBox" />

  <MyBox title="Projects">
    <Text str="hello" />
  </MyBox>
</component>
```

Generated code assigns a `pN` alias to `myapp/components`:

```go
package pages

import (
    tux "github.com/open-portfolios/codefolio/pkg/tux"
    builtin "github.com/open-portfolios/codefolio/pkg/tux/builtin"
    p1 "myapp/components"
)

func (self *dashboard) Build(ctx tux.BuildContext) tux.Component {
    return builtin.Container(
        builtin.ContainerProps{},
        p1.Box(
            p1.BoxProps{
                Title: "Projects",
            },
            builtin.Text(
                builtin.TextProps{
                    Str: "hello",
                },
            ),
        ),
    )
}
```

The generated call is `p1.Box(...)`, not `p1.MyBox(...)`. `alias` only affects the XML tag name. It does not affect the Go constructor name.

If there is no naming conflict, `alias` can be omitted:

```xml
<import package="myapp/components" component="Box" />

<Box title="Projects" />
```

The mapping above is:

| XML tag | Go call        |
| ------- | -------------- |
| `Box`   | `builtin.Box`  |
| `Text`  | `builtin.Text` |
| `MyBox` | `p1.Box`       |

## 7. Component Nodes

Except for tux meta nodes, every XML node is a component call.

Component nodes must be uppercase because they correspond to exported Go constructors:

```xml
<Box>
  <Text str="hello" />
</Box>
```

Generates:

```go
builtin.Container(
    builtin.ContainerProps{},
    builtin.Box(
        builtin.BoxProps{},
        builtin.Text(
            builtin.TextProps{
                Str: "hello",
            },
        ),
    ),
)
```

Lowercase nodes are reserved for tux meta nodes. The first version has `<component>`, `<import>`, and `<children />`.

## 8. Container

`Container` is a foundational builtin component in `tux/builtin`.

It has no visual semantics such as style, layout, border, color, or padding. It only wraps multiple components into a single component and holds those children in order.

The XML compiler makes every component's `Build(ctx)` return a `builtin.Container(...)` by default.

For example:

```xml
<component package="components" name="example">
  <Text str="hello" />
</component>
```

Generates:

```go
func (self *example) Build(ctx tux.BuildContext) tux.Component {
    return builtin.Container(
        builtin.ContainerProps{},
        builtin.Text(
            builtin.TextProps{
                Str: "hello",
            },
        ),
    )
}
```

An empty component also generates an empty `Container`:

```xml
<component package="components" name="empty">
</component>
```

Generates:

```go
func (self *empty) Build(ctx tux.BuildContext) tux.Component {
    return builtin.Container(
        builtin.ContainerProps{},
    )
}
```

Therefore, `Build(ctx)` always returns a component and does not need a special branch for “no children”.

## 9. Children Slot

`<children />` specifies where external child components should be inserted inside a composite component XML file.

For example, define a `Panel` composite component:

```xml
<component package="components" name="panel">
  <Box str="panel">
    <Text str="@{self.title}" />
    <children />
  </Box>
</component>
```

The handwritten constructor receives children:

```go
type PanelProps struct {
    Title string
}

type panel struct {
    tux.Composite

    title    *tux.State[string]
    children []tux.Component
}

func Panel(props PanelProps, children ...tux.Component) tux.Component {
    return &panel{
        title:    tux.NewState(props.Title),
        children: children,
    }
}
```

The XML compiler turns `<children />` into a `builtin.Container(...)` and places `self.children...` inside it:

```go
func (self *panel) Build(ctx tux.BuildContext) tux.Component {
    return builtin.Container(
        builtin.ContainerProps{},
        builtin.Box(
            builtin.BoxProps{
                Str: "panel",
            },
            builtin.Text(
                builtin.TextProps{
                    Str: self.title.Get(ctx),
                },
            ),
            builtin.Container(
                builtin.ContainerProps{},
                self.children...,
            ),
        ),
    )
}
```

Rules:

- `<children />` is a tux meta node, not a normal component.
- `<children />` must be self-closing.
- `<children />` can only appear where component children are expected.
- `<children />` generates `builtin.Container(builtin.ContainerProps{}, self.children...)`.
- Since `<children />` becomes an ordinary component, it can appear anywhere in a children list.
- If a composite component does not need to pass through external children, omit `<children />`.

## 10. Props Compilation Rules

Each component constructor receives at least props:

```go
func Xxx(props XxxProps) tux.Component
```

If a component needs child components, add a variadic children parameter:

```go
func Xxx(props XxxProps, children ...tux.Component) tux.Component
```

Even if a component has no props, it must still have an empty `XxxProps`:

```go
type XxxProps struct{}
```

Calls pass `XxxProps{}`.

Constructors may also return concrete types as long as the type implements `tux.Component`:

```go
func Xxx(props XxxProps) *xxx
```

XML props must be camelCase.

The Go `XxxProps` field name is produced by uppercasing only the first character of the XML prop name:

| XML prop    | Go field    |
| ----------- | ----------- |
| `str`       | `Str`       |
| `value`     | `Value`     |
| `onChange`  | `OnChange`  |
| `autoFocus` | `AutoFocus` |
| `maxWidth`  | `MaxWidth`  |

Example:

```xml
<Input state="{self.name}" autoFocus="{true}" />
```

Generates:

```go
builtin.Input(
    builtin.InputProps{
        State:     self.name,
        AutoFocus: true,
    },
)
```

The compiler does not need to know whether `InputProps` exists, and it does not need to check field types. The Go compiler performs the final type check.

## 11. Attribute Value Compilation Rules

Attribute values have three forms.

The first form is a normal string:

```xml
<Text str="hello" />
```

Generates:

```go
builtin.Text(builtin.TextProps{
    Str: "hello",
})
```

The second form is an ordinary Go expression:

```xml
<Button onPress="{self.submit}" />
```

Generates:

```go
builtin.Button(builtin.ButtonProps{
    OnPress: self.submit,
})
```

The third form is State read sugar:

```xml
<Text str="@{self.title}" />
```

Generates:

```go
builtin.Text(builtin.TextProps{
    Str: self.title.Get(ctx),
})
```

Summary:

| XML value   | Go output       |
| ----------- | --------------- |
| `"content"` | `"content"`     |
| `"{expr}"`  | `expr`          |
| `"@{expr}"` | `expr.Get(ctx)` |

Restrictions:

- `{...}` must occupy the whole attribute value.
- `@{...}` must occupy the whole attribute value.
- String interpolation is not supported.
- `@{expr}` mechanically generates `expr.Get(ctx)`.
- The compiler does not check whether `expr` is `*tux.State[T]`.
- Complex calculations should be written as Go methods and referenced with `{self.method()}`.

## 12. XML Does Not Provide Control Flow

XML only describes static component structure. It does not provide `if`, `for`, or any other control flow.

If dynamic logic is needed, write Go code.

For example, do not write conditional branches in XML. Instead, write a handwritten component or Go method and reference it from XML.

This keeps:

- The XML compiler simple.
- The compiler independent from Go type analysis.
- Dynamic logic in Go, where it is easier to debug.
- Generated code predictable.

## 13. Props Are Only An Argument Container

`Props` is not component state. It is only a constructor argument container.

Component structs must not store props directly:

```go
// Not allowed
type input struct {
    props InputProps
}
```

Components must split props into their own fields:

```go
// Allowed
type input struct {
    state *tux.State[string]
}

func Input(props InputProps) tux.Component {
    return &input{
        state: props.State,
    }
}
```

The reason is that props are only a structure used at the constructor call boundary. A component instance should maintain explicit internal fields instead of holding the props object long-term.

## 14. State And Events

`State[T]` stores reactive state:

```go
type State[T any] struct {
    // internal
}

func NewState[T any](initial T) *State[T]
func (s *State[T]) Get(ctx BuildContext) T
func (s *State[T]) Set(v T)
func (s *State[T]) Update(fn func(T) T)
```

`Get(ctx)` reads state and creates a subscription.

`Set(v)` and `Update(fn)` modify state and trigger subscriber rebuilds.

Most display components read state with `@{self.xxx}`, which generates `self.xxx.Get(ctx)`. Common two-way binding components such as `Input` can receive `*tux.State[string]` directly, so they use a normal expression like `{self.name}` to pass the state object. When input content changes, `Input` updates that state directly.

Example:

```xml
<Input state="{self.name}" />
```

Equivalent generated code:

```go
builtin.Input(builtin.InputProps{
    State: self.name,
})
```

Data flow:

```text
Build(ctx) reads State or passes State to components that support binding
  -> atomic components receive props
  -> user input triggers Input to update State internally
  -> State dirties its subscribers
  -> affected components Build again
```

The `Render(...)` phase receives a `RenderContext` and paints into it. It must not create state subscriptions; state reads that affect component structure or props belong in `Build(ctx)`.

## 15. Component Internals

All tux components implement the same interface:

```go
type Component interface {
    Build(ctx BuildContext) Component
    Render(build BuildContext, render RenderContext) error
}
```

This interface represents two kinds of components.

The first kind is a composite component. It does not render directly; it returns a child component tree from `Build(ctx)`.

The second kind is an atomic component. It paints directly into a `RenderContext` from `Render(...)`.

`RenderContext` is the low-level rendering target:

```go
type RenderContext interface {
    Paint(row, column int, b byte)
    Flush() error
}
```

The current debug renderer implements this interface with a two-dimensional byte buffer. A future terminal renderer can implement the same interface with terminal cells, style, diffing, and flushing.

Runtime rules:

- Composite components return another component from `Build(ctx)` and usually inherit the no-op `Composite.Render(...)`.
- Atomic components return nil from `Build(ctx)` and implement `Render(...)` to paint into the render context.
- Components that own children, such as `Container`, decide how to expand and render those children.
- If `Build(ctx)` returns the same component value, tux treats it as a composition cycle and panics.

## 16. Atomic And Composite

tux provides two helper embedded types.

Atomic components embed `tux.Atomic`:

```go
type Atomic struct{}

func (Atomic) Build(ctx BuildContext) Component {
    return nil
}

func (Atomic) Render(build BuildContext, render RenderContext) error {
    panic("tux: atomic component must implement Render")
}
```

Composite components embed `tux.Composite`:

```go
type Composite struct{}

func (Composite) Build(ctx BuildContext) Component {
    panic("tux: composite component must implement Build")
}

func (Composite) Render(build BuildContext, render RenderContext) error {
    return nil
}
```

This guarantees:

- An atomic component that forgets to implement `Render(...)` panics at runtime.
- A composite component without generated `Build(ctx)` panics at runtime.
- Atomic components have no component-expansion logic by default.
- Composite components have no direct-rendering logic by default.

## 17. Atomic Components

Atomic components are handwritten Go components that paint directly into a `RenderContext`.

Example:

```go
type TextProps struct {
    Row    int
    Column int
    Str    string
}

type text struct {
    tux.Atomic

    row    int
    column int
    str    string
}

func Text(props TextProps) tux.Component {
    return &text{
        row:    props.Row,
        column: props.Column,
        str:    props.Str,
    }
}

func (t *text) Render(build tux.BuildContext, render tux.RenderContext) error {
    for i := 0; i < len(t.str); i++ {
        render.Paint(t.row, t.column+i, t.str[i])
    }
    return nil
}
```

Atomic components may receive children. Whether those children are used is decided by that component's own `Render(...)` implementation.

`Container` is the first builtin example of this rule: it is atomic, but its render method expands each child through `Build(ctx)` until an atomic artifact is reached, then calls that child's `Render(...)`. If a child build returns itself, `Container` panics because that is a composition cycle.

## 18. Composite Components

Composite components usually consist of a user-written state struct and an XML-generated `Build(ctx)` method.

Handwritten part:

```go
type home struct {
    tux.Composite

    title *tux.State[string]
}
```

Generated part:

```go
func (self *home) Build(ctx tux.BuildContext) tux.Component {
    return builtin.Container(
        builtin.ContainerProps{},
        builtin.Text(builtin.TextProps{
            Str: self.title.Get(ctx),
        }),
    )
}
```

`Build(ctx)` can be called many times. It is a projection from current state to component tree.

## 19. Local Rebuilds

tux does not use whole-app dirty, meaning a single state change does not mark the entire application for rebuild.

Here, dirty means “this mounted element depends on data that changed, so it needs to execute `Build(ctx)` again”.

`State.Get(ctx)` subscribes the current `BuildContext`'s mounted element.

`State.Set(...)` only dirties those subscribers.

State update flow:

```text
State.Set(...)
  -> dirty subscribers
  -> scheduler rebuild dirty elements
  -> Build(ctx) regenerates component tree
  -> reconcile child component
  -> atomic Render(...) paints into RenderContext
  -> buffer diff / terminal flush
```

Subscribers are bound to internal mounted elements, not temporary component values. `Build(ctx)` may create a new component tree each time, so component values are not stable identities.

## 20. Key

tux may have a key mechanism, but keys are maintained by the framework. Users do not need to specify them manually.

Keys are used for mounted element identity and reconciliation. Users do not need to write `key` as a normal XML prop.

If stable identity for lists or dynamic children is needed later, an explicit key mechanism can be designed separately.

## 21. Non-Goals

The first version explicitly does not do the following:

- No GSX.
- No Go function bodies inside XML.
- No `if` / `for` control flow inside XML.
- No string interpolation.
- No requirement for the XML compiler to read external Go types.
- No requirement for the XML compiler to check whether props fields exist.
- No requirement for the XML compiler to check whether `@{...}` is state.
- No whole-app dirty.
- No state subscription during `Render(...)`.
